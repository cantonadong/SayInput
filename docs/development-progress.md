- WASAPI 麦克风枚举、16 kHz PCM 采集、音量计算与可选预热。
- 有界有序音频管线：连接期间保留开头音频，松开后排空尾部；溢出或奇数字节 PCM 会终止会话，避免发送损坏或截断数据。
- 火山引擎 WebSocket 协议、串行发送、单接收循环、压缩/长度校验和错误处理。

- 会话协调器处理重复按键、Starting 阶段松开、取消、空 final、失效目标和连续会话；100 次连续会话测试确认每个 final 只上屏一次。

## 本轮发现并解决的问题

### DPAPI 测试在文件沙箱内失败

现象：受限环境运行完整测试时，5 个 `DpapiCredentialStoreTests` 抛出 `CryptographicException`，错误提示当前线程可能没有加载用户配置；其余 80 个测试通过。

定位：`APPDATA`、`LOCALAPPDATA` 和 `USERPROFILE` 值正常，异常发生在 `ProtectedData.Protect`。在常规 Windows 用户上下文使用相同代码和测试数据运行后，非硬件测试全部通过。

结论：这是执行沙箱无法访问当前 Windows 用户 DPAPI 密钥配置造成的环境失败，不是代码回归。DPAPI 相关测试必须在正常用户上下文运行，不能通过改用明文、机器级密钥或跳过安全测试来规避。

### 保存后立即退出可能丢配置

原流程先调用 `StopAndDrainAsync()`，再等待设置窗口的活动保存。若保存仍在 `runtime.SuspendAsync(true)` 中、尚未进入配置写队列，写队列会先被标记停止，随后保存被拒绝并被 UI 捕获。

修复：退出顺序改为等待托盘切换、等待活动保存、封闭并排空写队列，然后停止测试、预热和运行时。新增顺序回归测试。

### 剪贴板暂时占用导致回退直接失败

原实现仅在恢复剪贴板时捕获一次 `ExternalException`，读取、设置和手动复制遇到剪贴板占用会立即失败。

修复：对剪贴板读写加入统一的有限重试；连续失败 5 次后仍抛出原异常，避免无限阻塞。新增“第三次成功”和“第五次停止”测试。

### 真实火山引擎实验被本机网络策略阻断

用户授权使用仓库根目录下被 `.gitignore` 排除的 `key.txt` 做真实调用。文件不是纯 key，而是“中文标签＋全角冒号＋末尾 ASCII API Key”；实验工具必须只提取末尾连续可打印 ASCII token，且不得回显、写入日志或文档。正式应用设置界面仍应填写纯 API Key。

2026-09-15 实验结果：`openspeech.bytedance.com` DNS 解析正常，`Test-NetConnection` 对 443 端口成功；临时 .NET 8 WebSocket 最初被 SimpleWall 以 `SocketException 10013` 拒绝。用户放行正式 EXE 并按全局规则完全退出、重启后，应用到达火山引擎。官方四种流式 Resource ID 探测确认：该 API Key 未开通 1.0 小时版和并发版，已开通 `volc.seedasr.sauc.duration`，与用户提供的 LazyTyper“流式识别 2.0”信息一致。配置已通过正式设置界面保存，API Key 由当前 Windows 用户 DPAPI 加密；随后全新进程不读取 `key.txt`、仅使用已保存配置再次连接成功。

## 可复用经验

- Windows DPAPI 的测试结论必须结合用户配置是否真正加载来判断。先用相同命令在正常用户上下文复现，再决定是否改代码。
- 关闭异步应用时，先等待所有可能产生写入的上游任务，再关闭写入入口并排空队列。只等待队列中已有任务无法覆盖“已开始但尚未入队”的操作。
- 剪贴板是共享且易被短暂锁定的系统资源。读取、设置、清空和恢复都应使用相同的短时有限重试，并保留最终失败信号。
- `SendInput` 返回部分成功时，不能自动切换到完整文本的备用注入，否则用户会得到重复或拼接文本；应报告失败并保留可恢复文本。
- 语音服务的 utterance definite 不等于整个会话完成。只有客户端发送音频结束后收到的 terminal 帧才能结算 final。
- 真实硬件、云端和跨应用体验不能用模拟测试替代。自动测试负责协议、边界和生命周期，人工验收负责麦克风、网络、焦点和目标应用兼容性。
- 当前仓库跟踪生成文件，运行测试或发布会产生大量状态变化。提交时应逐项暂存源码、测试、文档、脚本和有意发布的产物，避免 `git add -A`。

### 本轮遇到的坑与可复用经验

- WPF XAML 的 `Icon="resources/icon.ico"` 会按 Pack Resource 解析，而发布配置把图标作为 Content 复制，导致窗口创建时报通用启动错误。运行时用绝对文件路径创建 `BitmapFrame`，并使用 `BitmapCacheOption.OnLoad` 后冻结对象，可同时避免文件锁和资源解析差异。
- 静音必须保存每个 Render 端点原状态，部分静音失败时立即回滚；停止时不能简单“全部取消静音”，否则会破坏用户原有设置。
- 提示音顺序涉及用户可感知的边界。开始音播放完成后再静音，停止时先恢复输出再播放停止音；异步热键回调需要串行门，避免快速连按交叉执行。
- 纯绿色迁移应采用“目标缺失才复制 + 同目录临时文件后原子改名”，防止覆盖便携配置或在中断时留下半文件。

## 2026-09-15：修复点按录音的 STA 异常

- 用户首次测试点按右 Alt 时收到“调用线程必须为 STA，因为许多 UI 组件需要”的异常，录音未启动。根因是热键 Hook 位于后台线程，提示音和静音的异步等待又将续体切到线程池；`LazyRecordingOverlay` 随后在该非 STA 线程首次创建 WPF `RecordingOverlay`。
- `LazyRecordingOverlay` 现在捕获应用的 WPF Dispatcher。首次 `Show` 和关闭操作若来自热键或线程池，会同步调度回 UI STA 线程；音量、partial 和状态更新仍由已有窗口自身异步调度。
- 新增真实 STA Dispatcher 回归测试：从线程池调用懒加载 `Show`，断言工厂实际运行在 STA 线程。测试在修复前因缺少 Dispatcher 参数编译失败，修复后定向测试 1/1 通过；完整 Release 非硬件测试 114/114 通过（Core 15、Volcengine 28、Windows 71）。
- 首次发布因正在运行的托盘进程锁定目标 DLL 而失败；完全终止旧进程后重新发布成功，并按 SimpleWall 全局规则启动新进程。当前仅一个新进程运行，启动后约 60.8 MB working set / 15.3 MB private bytes。
- 用户看到的“169k”若来自任务管理器内存列，通常代表约 169,000 KB（约 165 MB working set），不是 169 KB。设置窗口一旦创建，即使隐藏到托盘，WPF 视觉树与运行时仍驻留；后台全新启动且不打开设置时本轮测得约 61 MB。

### 可复用经验

- 懒加载 UI 只延迟分配，不会自动保证线程模型。工厂可能被首次调用者所在的任意线程执行；WPF 对象的创建、显示和销毁必须显式绑定其 Dispatcher。
- 发布到正在运行的 framework-dependent 或 self-contained 目录时，Windows 会锁住已加载 DLL。发布脚本前应先完全停止旧进程，并把“成功生成输出”作为启动新版的前置条件。

## 2026-09-15：录音与处理状态精灵动画

- 用户提供的 `icon/rec.png`（1540×165）和 `icon/process.png`（1875×205）实际都是横向 8 帧精灵图，不是带时间轴的多帧 PNG。保留原文件并随包复制到 EXE 同级 `resources/status`，未转 GIF、未拆成 16 个小文件。
